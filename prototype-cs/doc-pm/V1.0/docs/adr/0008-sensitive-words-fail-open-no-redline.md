# 敏感词过滤：商城词库不可达时 fail-open 全放行，不自留红线最小集

承接 ADR-0007（词库归商城）。**商城敏感词库不可达时，OCS 一律 fail-open 放行消息，不在本地自留任何「红线最小集」（涉政/暴/恐/违法）做兜底拦截**。OCS 是敏感词的**纯消费方**——本地零词库、零红线常量。

**为什么**：① 单一数据源原则——词库只认商城一处，OCS 不引入第二份本地词库（哪怕几条红线），避免双源口径分裂与维护负担（与 ADR-0007 同一逻辑的延续）；② 拒绝 fail-closed（全堵）——客服系统可用性不能绑死在外部词库可用性上，商城一抖动就全线瘫痪不可接受；③ 明确接受 fail-open 的合规代价：商城宕机窗口期内敏感内容（含涉政/违法）可能被发出，事后靠留痕 + 审计追溯，不靠实时拦截兜底。

## 后果（必须正视）

- **合规风险显式承担**：外部词库不可达 = 过滤真空期。需在风险登记 / 法务评审中标注此取舍，不可假装「最坏也兜得住」。
- **商城词库的可用性 SLA 是 OCS 合规能力的上限**：商城必须保证高可用 + 快速同步/调用；OCS 侧需埋「词库不可达」告警（fail-open ≠ 静默放行，要记录 + 告警，见 PRD §设置.2.2 已有的 fail-open 告警口径）。
- **不可达检测口径**：实时调用超时 或 同步缓存过期/拉取失败，二者都算「不可达」→ 触发放行 + 告警（具体毫秒阈值属工程实现，非本 ADR 约束）。
- 放行期间的消息**仍落库留痕**（原文不丢），供事后审计/质检回溯——留痕是底线，实时拦截不是。
- 本 ADR 与「自留红线」方案（A）的取舍已记录；若上线后发生涉政内容漏发事故，重启 A 方案是已知的补救路径（成本：新增本地红线常量 + 去重逻辑）。
