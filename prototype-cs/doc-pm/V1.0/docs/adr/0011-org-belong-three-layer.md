# 渠道归属：两层模型 → 三层（企业客户 / 品牌商城 / 应用端）

V2.2 已确立「渠道两层模型」（父=品牌商城、子=应用 H5/PC/小程序）。本期在客户会话信息中补充 3 个归属字段，把该模型**扩展为三层归属**：

```
企业客户（顶层，组织维度）   客户A / 客户B / 客户C
   └─ 品牌商城（中层）        品牌商城1 / 品牌商城2 / 品牌商城3
        └─ 应用端（叶，会话入口） 小程序 / H5 / PC
```

- **应用端 + 品牌商城** = 沿用 V2.2 两层，细化取值为枚举（应用端不再只有 H5，补齐 小程序/PC）。
- **企业客户** = 新增顶层。每条会话/用户归属到某「应用端」叶节点，逐级上卷到品牌商城、企业客户。
- 取值字典：企业客户={客户A,客户B,客户C}；品牌商城={品牌商城1,品牌商城2,品牌商城3}；应用端={小程序,H5,PC}。

**为什么**：
- 业务诉求是「会话/客户信息里要能看到来自哪个企业客户、哪个品牌商城、哪个应用端」——三个维度天然构成**组织→商城→进线入口**的父子层级，平铺成三个独立标签会丢掉归属关系（无法回答「品牌商城1 属于哪个企业客户」）。
- 应用端、品牌商城两层 V2.2 已定义，本期只是**补齐取值**（应用端从「仅 H5」扩到 小程序/H5/PC）；真正的新维度是「企业客户」。
- 列表信息密度有限 → 会话类列表（历史会话/转接/评价/留言/AI报表）只显**应用端叶层**；完整三层归属只在**客户身份面**（客户信息页、工作台右栏、会话详情弹窗）展示。

## 后果

- **展示**：客户信息页个人资料卡、工作台右栏基础信息、会话详情弹窗各加「企业客户/品牌商城/应用端」三行；历史会话渠道列改「应用端」取值 + 新增应用端筛选下拉；转接/评价/留言行追加应用端标识。原「来源渠道/注册渠道」（值=微信小程序）语义并入应用端（微信小程序→小程序）。
- **不建顶栏切换器**：本轮不做「企业客户/品牌」全局切换（属架构级工作，后续单列）。

## ⚠️ 待后端确认（本 ADR 标注为 proposed 的原因）

现有后端模型：`customers` 表 = 租户，13 张核心表经 `customer_id` 做**多租户隔离**，且 V2.2 将「品牌商城」按 `customer_id` 归属（单租户部署下品牌商城恒定）。引入「企业客户」顶层后，需后端明确：

1. **企业客户是否 = 把多个 `customer_id`/品牌商城租户归组的「超级租户」**？若是，则打破现有「一对一 customer_id = 租户 = 品牌商城」模型，需新增企业客户表 + 上挂关系。
2. **数据隔离边界**：客服可见/操作的数据按「企业客户」隔离还是「品牌商城」隔离？跨品牌商城/跨企业客户的会话是否可在同一工作台混合接待？
3. **应用端落库**：应用端（小程序/H5/PC）是否落到 `entry_channel` 单字段，还是 `customer_chat_sessions` 新增独立列？

以上未定前，原型仅做**展示层**归属（前端 mock 三层取值），不涉及后端表结构改动。后端方案落定后本 ADR 转 `accepted` 并回填存储/隔离结论。
