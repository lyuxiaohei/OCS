# 角色模型：拆分「客服主管」与「系统」，不用 SYS 一码双义

一期后台把动作发起方明确拆成 4 个角色 **C / A / S / SYSTEM**，而不再用 `SYS` 同时指代「客服主管（人）」和「后端自动（代码）」。`S` 是带更高权限的 admin（后端 `MessageSourceAdmin=1`），`SYSTEM` 是非人自动 actor（后端 `MessageSourceSystem=2`，如 cron 超时关闭 / TTL 回退 / 敏感词过滤 / WS 推送）。

**为什么**：旧稿 `SYS` 一码双义，导致状态机角色列 `A/SYS` 分不出「主管手点结束」还是「cron 超时关闭」，审计无法归因；且与后端既有的 4 源模型（`consts.go:97-102` User/Admin/System/Ai）自相矛盾。拆分后人/自动在每条状态迁移、每个 UC、每条审计日志里都可区分，且与后端逐字对齐。

## 考虑过的选项

- **①（采用）** 主管并入 A、SYS 只留作系统 → 实为「3 码但重定义」。被 ② 覆盖。
- **②（最终采用）** `C / A / S / SYSTEM` 四码：S=主管（人，source=1）、SYSTEM=系统（自动，source=2）。审计最清晰，代价是引入一个"后端消息源里存在、但旧稿没单列"的人角色。
- **③** 维持 `SYS` 双义。省事但审计歧义永久存在、与后端矛盾，否决。

## 后果

- 需重排所有 UC/状态机的角色列：人点操作（留言分配、知识库审核、系统设置、转接回退配置、差评追踪等）归 **S**；自动触发（超时关闭、TTL 回退、敏感词过滤、冷却防重、超时归跳过）归 **SYSTEM**。
- 测试账号「王小明/张小明/刘洋 = A/S」：S 即主管账号，不再是 SYS。
- 后端权限模型需有「主管」权限位（source 仍=1），无需新增消息来源。
- PRD 正文、CONTEXT.md、§二角色表、§六消息来源说明均按本 ADR 修订。
