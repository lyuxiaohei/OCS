# 转接生命周期：pending 源只读 / 交接写权全转 / 连环限深 3 / 离线宽限重分

一期转接在 PRD 原状态机（`pending → accepted/rejected/cancelled/timeout`）之外补齐四条产品逻辑：① 转接单 **pending 期间会话进入「转接中」中间态、源客服只读不可发**、用户侧提示"正在转接"、用户消息进队列；② 目标 **accepted 那一刻归属与全部写权限一并转移给目标**（发/撤回/脱敏/挂起/转接/结束），源仅留只读历史、队列消息转为目标未读；③ **允许连环转接，深度上限 3 跳**（原客服 + 最多 2 次），超限拒绝并提示、历史客服列展示全链 `A→B→C`、每跳独立转接单与独立 TTL；④ 失败回流：rejected/cancelled 回源恢复可发、timeout 走既定回退 3 选 1；**客服离线时名下活跃会话宽限期（默认 2 分钟）内重连则恢复、超时转排队重分**，用户侧即时提示"客服暂时离开"。

**为什么**：原 PRD 对 pending 窗口、交接、连环、离线全无定义，留下"双接待 / 消息错位 / 踢皮球 / 源离线卡死"四个高发风险。四条裁定的共同原则是**会话任一时刻单一属主**——只有一个客服对用户有写权限，归属转移即彻底交棒。

## 考虑过并否决的

- pending 期间源可继续聊（双接待）→ 双发言风险，否决。
- accepted 后源保留撤回权 → 与单一属主冲突、入口拧巴，否决。
- 连环禁止 / 无限 → 前者误伤合理二次转接、后者放任踢皮球，否决，取限深 3。
- 离线立即重分 / 不处理 → 前者误转抖线、后者让用户空等，否决，取宽限 + 超时。

## 后果

- 会话状态机需新增「转接中」条件（accept + 存在 pending 转接单），并在 accepted/rejected/cancelled/timeout 时正确解除（见 CONTEXT.md「转接中」）。
- 转接单需记录链路与跳数；历史会话客服列由"单名 / 双名"扩展为"全链 A→B→C"。
- WS 需在 accepted 时把队列消息作为目标未读下发；离线宽限与超时重分需 cron/WS 配合。
- 离线宽限期、连环深度上限为可配项，建议默认 **2 分钟 / 3 跳**。
- **连环深度计数边界（Q21 补）**：深度计数**只累加「客服主动转接」**；当 timeout 回退走「重新排队分配」时，**计数重置归零**——排队重分是路由引擎的系统兜底重分配，性质不同于客服间踢皮球，重分后新接手客服获得完整 3 跳额度。否则一个反复转接失败的会话会在系统侧被永久卡在限深边缘，谁接了都不能再转。

## 重新排队次数上限（Q1 补，2026-06-22）

「重排队重置计数」（Q21）解决了会话卡限深边缘，但打开了「重排无上限」的新口子——会话可能反复 timeout→重排→再 timeout，用户被无限转接、反复空等。**裁定**：同一会话累计「重新排队分配」达 **2 次**（可配）仍无客服稳定接手 → 触发终局兜底：优先回退给**在线的原客服**；原客服也离线则**关闭会话 + 向用户致歉 + 自动生成留言邀约**。每次重排与终局均落会话日志可审计。与「单一属主」原则一致：终局必须把会话交给一个确定的人，或干净关闭。

## 转接失败回流时，队列消息归属（Q4 补，2026-06-22）

转接中源只读、用户消息进队列（待目标接受转未读）。**失败回流**（rejected / cancelled / timeout 回退原客服）时，队列期间用户发的消息**一并退给原客服、作为未读**，绝不丢消息——原客服恢复后可见并继续服务。原则：用户消息只进不出，转接的任何结局都不能让用户消息消失。
