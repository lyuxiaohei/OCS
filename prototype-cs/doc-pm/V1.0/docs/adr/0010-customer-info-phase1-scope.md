# 客户信息一期范围：服务 + 基础 + 交易，行为(埋点)推 2 期

客户信息 360° 画像 4 Tab（基础/行为/交易/服务），**一期只做 3 个**：服务历史（OCS 自有）、基础信息（商城会员库）、交易记录（OMS）。**行为轨迹（埋点系统）推 2 期**，一期在页面上**灰显占位「即将上线」**（保留 4 Tab 框架，第 4 个置灰），不渲染真实行为数据。

**为什么**：
- **服务**零外部依赖（OCS 客服库），本就有；**基础**（商城会员）大概率一期要做（工作台右栏客户摘要要会员信息）；**交易**接口 `GET /api/user/transactions` 与工作台订单卡（US-MVP-17）共享，订单卡一期本就要做 → 交易 Tab **边际成本≈0**，只是多一个展示位。这 3 块正好覆盖客服**接待当下最需要的画像**（这人是谁、买了啥、之前问过啥）。
- **行为轨迹**（浏览/加购/收藏/搜索词）是售前营销视角，客服接待用不上那么频繁；且埋点系统是 4 源里**最可能不稳、排期最滑**的（独立团队、口径杂、历史包袱）。把它踢出一期关键路径，保 8 月底上线（V1.4）。
- 否决 A（全量 4 Tab）：埋点拖垮全线风险太高。否决 B（只服务+基础）：放着「免费」的交易接口不做，客户画像缺最核心的订单信息。

## 后果

- 一期客户信息页 = 3 个有效 Tab + 1 个灰显占位（行为）。灰显而非不渲染——告诉用户「这是完整画像的一部分，2 期补」，避免被当成「功能没做完」。
- 一期外部集成承诺 = **商城会员库（基础）+ OMS（交易）** 两源；服务来自 OCS 自有。埋点系统对接移至 2 期。
- 客户信息.2.1 的 4 Tab 数据源表：行为 Tab 标注「2 期，一期灰显占位」；交易 Tab 保留「与工作台订单卡共享接口」契约不重复定义。
- 客户信息.2.2「降级粒度」「超时阈值」等边界仍适用一期 3 个有效 Tab（按源独立降级）。
