## 一、需求功能清单梳理

`商城平台-2026Q3-Q4排期` 中的客服系统分**运营后台（客服端）**与**前端商城（用户端）**两大部分，按 **1 期-MVP / 2 期-体验提升 / 3 期-AI 智能化** 三期推进。

### A. 商城运营后台（客服端）

| 模块 | 关键功能 |
|---|---|
| 工作台 | 多渠道聚合工作台、待处理事项 |
| 会话管理 | 转接、智能路由分流、排队溢出、消息撤回、敏感词过滤、会话超时、离线留言、历史会话、消息预显(输入中)、三方会话、拉黑 |
| 客户信息 | 360°客户视图（基础/行为/交易/服务数据 + 标签体系） |
| 知识库 | FAQ、快捷回复、话术库、关键词联想 |
| 工单系统 | 工单（可选，现用 OMS） |
| 智能辅助 | AI 话术推荐、商品推荐、订单上下文、转人工意图识别 |
| 监控报表 | 实时监控面板、绩效看板、预警、会话量/渠道统计、机器人报表、服务质量报告、客户分析 |
| 配置管理 | 欢迎语、离线自动回复、客服账号、分流/技能组、角色权限(6 角色) |
| 渠道接入 | IVR 热线、邮件、抖音/小红书私信 |
| 机器人/AI | 商品/活动/售后知识库、转人工触发、知识库命中监控、**对话树可视化编辑(低代码)** |
| 智能客服核心 | 多轮意图识别(5 轮+)、知识图谱、NLP 多模态、文档解析、上下文记忆、AI 质检与会话摘要、无缝转人工 |
| 售前/售中售后 AI | 商品参数对比、促销解读、尺码推荐、个性化推荐、物流跟踪、订单查询、退换货引导、退差价/改地址 |

### B. 前端商城（PC/H5/小程序）

在线客服(文字/图片/语音 + 订单/商品卡片)、电话呼叫、多入口(商详/订单/购物车/物流/个人中心/悬浮窗)、已读未读、断线重连、FAQ 机器人、猜你想问、自助办理、排队提示、服务评价、富媒体消息、大模型智能客服基础版。

> **结论先行**：单一开源系统**无法 100% 覆盖**（尤其 3 期 AI：知识图谱、多模态、大模型）。最优解是「**客服平台底座 + AI/RAG 层**」组合。

## 二、开源系统选型概览

### 核心候选（Java 系）

#### 🥇 Bytedesk 微语 — 覆盖度最高
- **仓库**：https://github.com/Bytedesk/bytedesk
- **技术栈**：Java + Spring Boot，多端有 UniApp/小程序/H5/Web 实现
- **许可**：AGPL-3.0（根目录）/ **BSL 1.1**（源码文件头，详见第四部分许可核实）
- **功能匹配**：多渠道、智能路由、坐席工作台、质检、知识库、**工单+SLA**、数据报表、**AI Agent(RAG+函数调用+大模型)**、呼叫中心、多端访客 SDK
- **维护**：✅ 很活跃（v2.5.2，2026-05）

#### 🥈 春松客服 CSKeFu — 老牌专业客服
- **仓库**：https://github.com/cskefu/cskefu
- **技术栈**：Java + Spring Boot
- **许可**：Chunsong Public License v1.0（基于 Apache 2.0，允许免费商用 + 二开，第 4(d) 条禁止破坏其付费/计费机制）
- **功能匹配**：多渠道、坐席工作台(自动分配/转接/弹屏)、CRM、知识库、质检、报表、机器人(需对接 Chatopera 云)
- **维护**：⚠️ 开源版 v8.x 已停止活跃维护，AI 能力弱

#### 🥉 完整业务的客服系统（zhengyj98/agent）— 协议最宽松
- **仓库**：https://gitee.com/zhengyj98/agent
- **技术栈**：Java + MySQL + Spring/Hibernate
- **许可**：**Apache-2.0**（真正无传染性，免费商用 + 二开零限制）
- **功能匹配**：CRM、工单、客服管理、聊天、机器人对接、微信/QQ/网页/WAP/APP 接入、满意度评价
- **维护**：⚠️ 小型项目（164 star），活跃度低，适合做二开基底

### AI / 大模型层候选（覆盖 3 期智能客服）

| 系统 | 语言 | 许可 | 说明 |
|---|---|---|---|
| **MaxKB4j** (taishan666/MaxKB4j) | **Java** | GPLv3 | 对标 Dify/FastGPT 的 Java 版 RAG+LLM 工作流，可视化编排、智能问答 |
| MaxKB (1Panel-dev/MaxKB) | Python+Vue | GPLv3 | 原版，企业级智能体平台，社区庞大 |
| Dify / FastGPT / RAGFlow | 非 Java | 开源 | 成熟 RAG/Agent 平台，可 API 集成 |

**IM 通讯底座**（若需自建会话内核）：野火 IM WildfireChat（Java，社区版免费商用，高级功能付费）。

### 许可协议对比 ⚠️（直接关系「免费二开+商用」）

| 系统 | 许可 | 免费商用 | 闭源商业产品可用？ |
|---|---|---|---|
| zhengyj98/agent | Apache-2.0 | ✅ | ✅ 完全自由，无需开源 |
| 春松 CSKeFu | Chunsong v1.0 | ✅ | ✅ 基本自由（勿动其计费机制） |
| 野火 IM 社区版 | 社区免费商用 | ✅ | ✅ 核心免费，高级付费 |
| **Bytedesk** | **AGPL-3.0 / BSL 1.1** | ⚠️ | ⚠️ 自用 OK，转售/SaaS 禁止（2028 后转 Apache 2.0） |
| MaxKB4j / MaxKB | GPLv3 | ✅ | ⚠️ 分发衍生须开源（自用内网通常 OK） |

> **关键提醒**：商城是商业产品。**AGPL/GPL/BSL 系**自用内网一般合规，但作为对外 SaaS 或分发会触发开源/授权义务；若想彻底无忧应选 Apache 系（CSKeFu/agent）或购买商业授权。

### 3.4 关键结论

1. **共性硬伤（四者皆需二开）**：所有强电商耦合功能（订单/商品卡片、360°交易数据、商品推荐、物流/退换货机器人、各页面入口、抖音/小红书私信）**没有任何通用客服系统原生具备**，必须对接商城/OMS 自研，是**选型无关的固定成本**。
2. **按场景选择**：
   - 要功能最全 + 长期维护 → **Bytedesk** 或 **Bytedesk + MaxKB4j 组合**（组合是 3 期 AI 唯一高分方案）。
   - 要彻底免费、闭源无忧（Apache 系）→ **CSKeFu** + Dify/FastGPT(API)。
   - **agent**：协议最干净但功能/活跃度弱，仅适合做轻量二开基底。
3. **最优落地建议**：**Bytedesk 做客服底座 + MaxKB4j 补 3 期 AI**，综合得分最高（4.0），同栈 Java 集成顺；商用前预留授权确认。

## 四、源码架构与二开成本实测评估

> 源码已实际克隆并逐文件核实，附文件路径证据。

### 4.1 Bytedesk 微语 — 客服主底座

#### 技术栈（实测）
| 维度 | 选型 |
|---|---|
| 框架 / JDK | **Spring Boot 3.5.14 + Java 21**（开虚拟线程） |
| ORM / 数据库 | **JPA/Hibernate** + Liquibase；MySQL/PostgreSQL/Oracle/**人大金仓**/H2 五选一 |
| 缓存 / MQ | Redis(Jedis)+Caffeine 二级缓存（可关）；RabbitMQ / Artemis |
| 实时通讯 | **自研 Netty MQTT Broker** + STOMP/WebSocket |
| 搜索 / 向量 | **Elasticsearch**（IK 分词，全文+向量），可切 pgvector/milvus |
| AI | **Spring AI 1.1.7 + Spring AI Alibaba**，~24 家 LLM Provider，含 RAG/Function Calling/MCP/Agent |
| 工单流程 | **Flowable 7.2**（BPMN，SLA/升级/超时） |
| 呼叫中心 / 音视频 | **FreeSwitch ESL + IVR + MRCP**；**WebRTC + Janus** |

#### 架构
**单体模块化（modular monolith）**，非微服务，`starter` 打成单 Jar（端口 9003），模块间靠 Maven 依赖 + Spring 事件总线解耦。`modules/` 下 19 个业务模块；`channels/` 下 ~35 个电商/社媒渠道**全部为注释占位（无实现）**；`frontend/` 为空壳（真实前端在独立仓，已编译产物在 `starter/static/`，React + Ant Design Pro）。

| 关键模块 | 承载客服功能 |
|---|---|
| **core** | 消息引擎(44 种内容类型)、MQTT/WS、RBAC、组织、报表、MQ |
| **service** | 在线客服核心：访客/坐席/排队/路由/技能组/转接/留言/工作台 |
| **ai** | AI Agent、24 家大模型、RAG（ES 全文+向量+重排） |
| **kbase** | 知识库/FAQ/快捷回复/自动回复 |
| **ticket** | 工单 + **SLA**（Flowable） |
| **crm / call / webrtc** | 客户线索/呼叫中心 IVR/视频客服 |

#### 分层（高度规整，二开学习曲线低）
每个实体一套固定骨架：`Entity → Repository → Specification → Request/Response → RestService → RestController(/api/v1/**) → EventListener → Permissions → Initializer`。复制骨架即可新增模块。

#### ⭐ 关键正面发现：电商语义是一等公民
`modules/core/.../message/content/` **内置 7 种电商消息类型**（已核实）：`GoodsContent`、`OrderContent`(含地址/支付/快照)、`LogisticsContent`、`PayContent`、`RefundContent`、`QuotationContent`、`RateContent`，`MessageTypeEnum` 含 GOODS/ORDER/LOGISTICS/PAY/REFUND/RATE 及状态。**这把「订单/商品卡片交互」从重二开降为低二开**。配置层还预留了微信小程序商品/订单跳转路径。

#### ⚠️ 关键风险：许可证冲突（已核实）
- 根 `LICENSE` = **AGPL-3.0**
- 但**每个 .java 文件头 + `starter/LICENSE`** = **Business Source License 1.1（BSL，官方明示「非开源」）**，横幅写明：「**严禁用于销售、二次销售或者部署 SaaS 方式销售**」。
- BSL「Additional Use Grant」：不得用作面向第三方的 "Document/SaaS Service"；**Change Date = 2028-01-01 后自动转 Apache 2.0**。
- 配置含 `bytedesk.licenseKey`，暗示商业功能需购买授权。

> **对本场景的解读**：给**自有商城**做客服（自家坐席服务自家顾客）属 BSL 的「企业内部自用」，**大概率允许**；被禁止的是把 Bytedesk 平台本身转售/做成 SaaS 卖给第三方。但 AGPL 与 BSL 并存存在法律歧义，**商用前必须邮件向作者(270580156@qq.com)书面确认以哪份为准**。2028 年后转 Apache 2.0 则彻底无忧。

### 4.2 MaxKB4j — AI/RAG 大脑

#### 技术栈（实测）
**Spring Boot 3.5.1 + Java 21（虚拟线程）+ MyBatis-Plus + PostgreSQL/pgvector + MongoDB(全文) + Caffeine（无 Redis）+ LangChain4j 1.15 + Sa-Token + Flyway + Vue3(内嵌)**；19 家大模型 Provider（DeepSeek/Ollama/OpenAI/通义/智谱/火山…），Groovy 沙箱执行工具。

#### 架构与核心
模块化单体（`maxkb4j-start` 单 Jar）。`api`/`service` 接口实现分离。核心能力：
- **RAG 管线**：文档解析(Tika/OCR)→切分→embedding(pgvector)→**混合检索(向量+全文+重排)**→多轮问题改写→生成。
- **可视化工作流引擎**：前端 LogicFlow 图存 `jsonb`，后端 **35+ 节点 Handler**（AiChat/SearchKnowledge/Condition/Loop/Http/**Mcp**/**NL2Sql**/IntentClassify…），`@NodeHandlerType` 注解**自动注册**，扩展节点成本极低。
- **应用=Agent**：SIMPLE / WORK_FLOW 两型，支持多 Agent 嵌套、长期记忆、MCP（既是客户端也是服务端）、OpenAI 兼容 `/chat/completions`、iframe/embed.js 嵌入。
- ⭐ **内置电商模板**：`e-commerce-pre-sale-assistant`、`e-commerce-after-sale-assistant`。

#### ⚠️ 关键缺口
- **完全无人工客服/坐席/工单**（grep `人工/坐席/工单/ticket/handoff` 零命中）——它只是 AI 层，转人工需对接外部。
- **无 Redis、会话在内存**——多实例水平扩展需自行改造分布式会话/缓存。
- **GPLv3**（分发衍生须开源；内网自用通常合规）。

#### 二开成本：**中**
商城知识库接入(低)、商品/订单**动态** RAG(中，用 HttpNode/NL2Sql/自定义节点查实时数据)、小程序对话 UI(中，小程序跑不了 embed.js 需自研)、**转人工全链路(高，需自建)**。

- RAG 向量检索：`maxkb4j-service/maxkb4j-knowledge/.../store/VectorStoreImpl.java`、`retriever/DataRetriever.java`、`maxkb4j-knowledge-api/.../mapper/EmbeddingMapper.xml`

**两种落地路径**：
- **路径 A（推荐先评估）**：仅用 **Bytedesk**，其自带 Spring AI RAG 若够用则**不引入 MaxKB4j**，架构最简、只需处理一份 License。
- **路径 B**：Bytedesk + MaxKB4j，AI 能力更强（可视化编排/多 Agent/NL2Sql），但需协调**两份 copyleft 许可**且多维护一套。

> **License 红线汇总**：Bytedesk=AGPL/BSL（自用大概率 OK，转售/SaaS 禁止，须作者确认）；MaxKB4j=GPLv3（自用 OK，分发须开源）。**若要彻底零顾虑**，可回退到 CSKeFu(Chunsong/类 Apache) + Dify/FastGPT。

## 六、总结与决策建议

1. **架构契合度**：Bytedesk 对电商客服契合度**罕见地高**（电商消息内置），是最佳底座；MaxKB4j 是同栈 Java 的强 AI 大脑但缺人工客服链路，两者互补。
2. **真正的成本**不在客服系统本身，而在**第五部分的 15 个商城/OMS 对接点** + **电商平台渠道对接**（最重）。
3. **决策前必办的一件事**：就 Bytedesk 的 **AGPL/BSL 许可冲突**书面联系作者确认自用边界（2028 后转 Apache 2.0）。
4. **彻底零许可顾虑的备选**：CSKeFu(类 Apache) + Dify/FastGPT，代价是开源版需自维护、AI 需外挂。

### 推荐落地组合优先级
1. **首选**：Bytedesk 底座 + MaxKB4j AI 层（功能最全、同栈 Java、最活跃）→ 规划许可确认/商业授权。
2. **彻底免费无传染**：CSKeFu 底座 + Dify/FastGPT(API)。
3. **轻量二开基底**：zhengyj98/agent(Apache-2.0) + Dify。

### 7.5 关键差异解读
- **A 比 B/B+M 多约 2.4 倍工时**（≈600 vs ≈245）。差距几乎全部来自 agent 的**底座改造（108 人日）**与**3 期 AI 从零自研（223 人日）**——这两块在 Bytedesk 上大多原生可用。
- **B 与 B+M 总工时几乎持平（245 vs 247）**，但组合把「3 期 AI」从 99→80 人日（MaxKB4j 可视化工作流/多 Agent/NL2Sql 原生），新增「双系统集成+分布式化」20 人日。**等价工时下，B+M 的 3 期 AI 交付质量明显更高**。
- **电商集成（BFF ≈35 人日）三底座几乎相同**——与底座无关的固定成本。
- **agent 的“省”是假象**：二开工时 ≈ 现代栈绿地重写量级（甚至更高）。**在 agent 上二开是负价值**。

### 7.6 工时结论
1. **不要选 agent 做二开底座**；唯一优势（Apache 许可）被「≈600 人日、技术栈全 EOL、核心卖点不可交付」抵消。规避许可风险宁可现代栈绿地自研，把 agent 当数据模型参考。
2. **首选 Bytedesk（≈245 人日）或 Bytedesk+MaxKB4j（≈247 人日）**；同量级工时下组合换来更强 3 期 AI，推荐组合（前提：确认 AGPL/BSL 自用边界）。
3. **若许可红线不可逾越**（须 Apache/无传染且对外转售）：CSKeFu + Dify/FastGPT，粗估 ≈350~400 人日。

> ⚠️ 以上为粗粒度估算（±30~40%），用于方案选型决策，非正式排期。
