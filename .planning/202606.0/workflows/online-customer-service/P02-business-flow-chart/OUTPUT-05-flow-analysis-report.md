## 3. 痛点与瓶颈识别

### 痛点 1：会话分配缺乏智能路由，排队效率低

- **描述**：当前仅有 `is_auto_accept` 简单开关，无法根据用户来源（entry_tag）、客服技能、负载均衡等维度进行智能分配。所有用户进入同一等待队列，高价值客户和普通客户无差异化服务。
- **受影响流程节点**：OUTPUT-01 节点 P（Default Assignment - Round Robin）；OUTPUT-03 路由子图 RT2→RT11（No 分支直接进手动队列）
- **关联功能 ID**：F-MVP-02
- **严重程度**：**P0 — 严重**。直接影响用户等待体验和客服工作效率，是 MVP 核心差异化能力。

### 痛点 2：离线场景用户完全无服务，体验断崖

- **描述**：当所有客服离线时，用户仅能看到 `offline_content` 文案，无法提交留言、无法获得自动回复、无法预期何时能得到响应。整个离线体验链完全缺失。
- **受影响流程节点**：OUTPUT-01 节点 H→L（离线后直接进入等待状态）；OUTPUT-04 Flow A 全部待建节点
- **关联功能 ID**：F-MVP-22、F-MVP-20、F-MVP-06
- **严重程度**：**P0 — 严重**。非工作时间（夜间、节假日）用户完全无助，直接导致用户流失。

### 痛点 3：消息安全合规缺失，无敏感词拦截

- **描述**：消息发送链路中无任何内容审核环节。用户或客服发送的消息直接入库和推送，存在违规内容（广告、辱骂、敏感词）风险，无过滤、拦截或告警机制。
- **受影响流程节点**：OUTPUT-03 消息管道 M4→M7（当前直接跳过敏感词检测节点）
- **关联功能 ID**：F-MVP-04
- **严重程度**：**P0 — 严重**。涉及平台合规要求，不做可能导致监管风险。

### 痛点 4：会话无超时机制，资源无法释放

- **描述**：会话创建后，若无客服主动关闭或用户主动结束，会话将永远保持 `accept` 状态。`cron.go` 框架已搭建但未实现超时扫描逻辑，导致无效会话占用客服名额和系统资源。
- **受影响流程节点**：OUTPUT-03 CronTasks C1→C6（全部待建）；OUTPUT-01 节点 V（Queue Timeout Overflow 仅覆盖排队超时，不覆盖已接通会话超时）
- **关联功能 ID**：F-MVP-05
- **严重程度**：**P0 — 高**。长期运行将导致客服并发数耗尽，影响系统可用性。

### 痛点 5：客户信息孤岛，客服盲聊

- **描述**：客服在服务用户时，无法获取用户的会员等级、交易记录、行为数据。仅能看到 `getUserInfo` 返回的基础字段（昵称等）。客服无法基于用户画像提供个性化服务，需要反复询问用户基本信息。
- **受影响流程节点**：OUTPUT-02 D0→D4（全部待建）；OUTPUT-03 External 子图 E1→E12（全部待建，Mock 数据阶段）
- **关联功能 ID**：F-MVP-07、F-MVP-08、F-MVP-09、F-MVP-10
- **严重程度**：**P1 — 中高**。影响服务质量但可通过 Mock 数据缓解，MVP 阶段可降级处理。

### 痛点 6：缺乏待办和预警机制，客服响应无监督

- **描述**：客服工作台无待处理事项面板，无法感知哪些会话长时间未回复、哪些用户在等待超时边缘。完全依赖客服人工记忆和逐一查看会话列表，效率低下且容易遗漏。
- **受影响流程节点**：OUTPUT-02 B0→B3（全部待建）
- **关联功能 ID**：F-MVP-01
- **严重程度**：**P1 — 中**。影响客服工作效率，但不阻塞核心业务流程。

### 痛点 7：知识库空白，FAQ 和话术库无数据基础

- **描述**：系统无知识库表和 FAQ 管理功能，快捷回复模板仅有简单分类（type 字段），无场景标签和知识库关联。用户端无常见问题推荐，所有咨询都需人工处理。
- **受影响流程节点**：OUTPUT-04 Flow C 全部节点（15 个待建）
- **关联功能 ID**：F-MVP-11、F-MVP-12、F-MVP-24
- **严重程度**：**P1 — 中**。知识库是多个下游功能（话术库、FAQ 推荐、AI 客服）的基础，延迟交付将连锁影响后续功能。

### 痛点 8：消息类型单一，无法发送富媒体卡片

- **描述**：当前消息类型仅支持 text、image、audio（未实现）、video、pdf、navigator、rate、notice，缺少 order_card、product_card、coupon_card 三种卡片消息类型。客服无法在对话中直接展示订单详情、商品信息或优惠券，需要通过文字描述或外部链接，效率低且用户体验差。
- **受影响流程节点**：OUTPUT-01 节点 AA→AC（三个卡片类型全部待建）；OUTPUT-02 E4→E6（三个发送卡片节点全部待建）
- **关联功能 ID**：F-MVP-17、F-MVP-18、F-MVP-19
- **严重程度**：**P1 — 中**。影响电商场景下的客服效率和用户转化，但 MVP 阶段可通过文字+图片替代。

## 4. 冗余环节识别

### 4.1 路由分配与手动接起可合并

- **现状**：OUTPUT-03 路由子图中，`is_auto_accept=No` 分支（RT11）进入手动等待队列，`is_auto_accept=Yes` 分支（RT3→RT5）进入自动路由。手动接起（RT13）需要客服从等待面板点击接起。
- **冗余点**：智能路由引擎上线后，`is_auto_accept` 二元开关应被路由规则完全替代。路由规则可以配置为"手动接起"策略（匹配条件：all → 动作：手动接起），无需保留独立的 `is_auto_accept` 字段和分支逻辑。
- **建议**：W1-2 路由引擎开发时，将 `is_auto_accept` 迁移为路由规则的一个策略类型（`strategy=manual`），消除二选一判断节点。

### 4.2 欢迎语触发与 enter 系统规则重叠

- **现状**：OUTPUT-03 规则引擎中，`GetEnterRule`（match=enter, is_system=1）负责进入会话时触发欢迎语。同时 `customer_admin_chat_settings.welcome_content` 字段也在会话创建时发送欢迎语。
- **冗余点**：两套机制可能重复发送欢迎消息——规则引擎发送一条，会话创建逻辑再发送一条。
- **建议**：统一由规则引擎的 enter 规则负责欢迎语发送，废弃 `welcome_content` 字段的独立发送逻辑。将 `welcome_content` 迁移为 enter 系统规则的默认回复内容。

### 4.3 会话状态判断分散

- **现状**：OUTPUT-03 会话生命周期中，会话状态（wait/accept/close/cancel）的判断分散在多个节点：S2（has assigned admin）、S4（is in manual queue）、S10（admin accepts）、S14（close trigger）。
- **冗余点**：每次判断都需查询 `customer_chat_sessions` 表，相同条件在不同入口重复查询。
- **建议**：引入会话状态缓存层（Redis），会话状态变更时同步更新缓存，减少数据库查询。

### 4.4 快捷回复与话术库场景分类重叠

- **现状**：`customer_chat_auto_messages` 表现有 `type`（分类）字段用于快捷回复模板的简单分组。MVP 需新增 `scene_tags`（场景标签）和 `knowledge_item_id`（知识库关联）字段。
- **冗余点**：`type` 和 `scene_tags` 可能导致同一模板存在两套分类维度，增加管理复杂度。
- **建议**：`scene_tags` 上线后，逐步将 `type` 的分类能力迁移到 `scene_tags`，最终废弃 `type` 字段。过渡期 `type` 作为一级分类、`scene_tags` 作为二级标签共存。

### 4.5 用户端聊天页面与入口嵌入的重复加载

- **现状**：用户端仅有独立聊天页面（`service-user/src/pages/index/index.tsx`），6 页面入口嵌入（F-MVP-16）需要在 6 个不同页面中嵌入咨询入口。
- **冗余点**：每个入口页面都需独立实现入口 UI 组件和 WebSocket 连接管理，可能导致代码重复。
- **建议**：抽取统一的 `ChatEntry` 组件（含入口按钮 + 连接初始化 + entry_tag 传递），6 个页面仅需引入组件并传入 `entry_tag` 参数。

## 5. 优化建议

### P0 级优化（阻塞 MVP 交付，必须在 W1-W2 完成）

#### 优化 1：统一会话路由框架，消除 is_auto_accept 硬编码

- **问题**：当前 `is_auto_accept` 是简单的布尔开关，无法支持按来源、技能组、负载等维度分配。直接在现有代码上扩展会导致条件分支爆炸。
- **方案**：新建 `customer_chat_route_rules` 表，支持 4 种策略（round-robin / idle-first / skill-based / manual），按优先级匹配。将 `is_auto_accept` 迁移为 `strategy=manual` 的一条默认规则。
- **功能 ID**：F-MVP-02
- **预期收益**：消除硬编码分支，为 W5-6 入口嵌入的 entry_tag 路由匹配提供统一框架。预计减少后续 30% 的路由相关开发量。

#### 优化 2：消息管道增加拦截中间件层

- **问题**：消息发送链路是直线型（接收→持久化→推送），无法插入敏感词过滤、内容审核等横切逻辑。
- **方案**：在 `send-message` 处理链中引入中间件模式：`validate → filter(敏感词) → persist → deliver`。敏感词中间件使用 DFA 算法，词库加载到内存，毫秒级响应。
- **功能 ID**：F-MVP-04、F-MVP-03（撤回也可通过中间件记录实现）
- **预期收益**：消息管道可扩展，后续增加内容审核、频率限制等功能无需修改核心逻辑。敏感词过滤延迟 < 1ms/条。

#### 优化 3：会话超时 Cron 与预警推送一体化实现

- **问题**：`cron.go` 已搭建框架但无业务逻辑，会话超时和预警是两个独立需求但共享扫描逻辑。
- **方案**：在 `cron.go` 中实现统一会话扫描：每 1 分钟扫描所有活跃会话，按配置的超时阈值分级处理。5 分钟未回复→推送预警给客服（WebSocket）；超时阈值→自动关闭会话+推送评价引导。
- **功能 ID**：F-MVP-05、F-MVP-01（待办面板预警部分）
- **预期收益**：一次扫描解决超时关闭和预警两个需求，避免重复定时任务。预计减少 50% 的定时任务开发量。

### P1 级优化（影响服务质量，W3-W5 完成）

#### 优化 4：离线场景链式设计，一次交付三个功能

- **问题**：离线自动回复（F-MVP-22）、离线留言提交（F-MVP-20）、留言管理（F-MVP-06）三者强依赖，分开设计容易导致接口不匹配。
- **方案**：按 OUTPUT-04 Flow A 的链式协同关系，设计统一的离线状态管理模块。Redis 检测到所有客服离线→触发 auto_rules u-offline 场景→发送留言引导卡片→用户提交→管理端待办展示。
- **功能 ID**：F-MVP-22 → F-MVP-20 → F-MVP-06
- **预期收益**：避免分批开发导致的接口不兼容。离线场景的端到端体验一致性提升。

#### 优化 5：外部数据层统一封装，Mock/真实透明切换

- **问题**：6 个外部接口（会员库、商品库、OMS、营销中心、埋点系统）若分散在各处调用，Mock/真实切换将非常困难。
- **方案**：实现统一的 `ExternalDataService` 接口层，封装 Mock 切换、缓存策略（Redis TTL）、超时控制（3s）、降级策略。每个外部接口独立配置 Mock 开关（`config.External.*.Mock`），支持混合模式。
- **功能 ID**：US-INT-01、US-INT-02、US-INT-03
- **预期收益**：2 期对接真实接口时仅需修改配置文件，零代码改动。Mock 阶段前端开发不受外部系统阻塞。

#### 优化 6：知识库提前至 W3 启动，支撑下游功能

- **问题**：知识库（F-MVP-11）是话术库改造（F-MVP-12）和 FAQ 快捷问题（F-MVP-24）的数据基础，若延迟交付将阻塞两个下游功能。
- **方案**：W3 开始知识库表设计和 CRUD 开发，同步准备种子数据（至少 30 条 FAQ）。知识库表设计时预留 `entry_tag`、`keywords`、`hit_count` 字段，直接为 FAQ 推荐和路由规则服务。
- **功能 ID**：F-MVP-11、F-MVP-12、F-MVP-24
- **预期收益**：知识库数据提前就绪，W6-7 FAQ 功能可直接对接，无需等待。

#### 优化 7：卡片消息类型统一 JSON Schema 设计

- **问题**：order_card、product_card、coupon_card 三种卡片消息类型若独立设计，前端渲染逻辑将高度重复。
- **方案**：设计统一的卡片消息 Schema：`{ type: "card", card_type: "order|product|coupon", payload: {...}, actions: [...] }`。前端实现统一的 `CardMessage` 渲染组件，按 `card_type` 分发到 `OrderCard`、`ProductCard`、`CouponCard` 子组件。
- **功能 ID**：F-MVP-17、F-MVP-18、F-MVP-19
- **预期收益**：减少重复代码约 60%，新增卡片类型（如 2 期的活动卡片）仅需新增子组件。

### P2 级优化（体验提升，不阻塞 MVP）

#### 优化 8：WebSocket 消息队列化，提升弱网体验

- **问题**：当前 WebSocket 消息直接发送，弱网环境下消息丢失风险高。断线重连后仅拉取历史消息，无法保证消息时序完整性。
- **方案**：客户端引入消息队列（IndexedDB/小程序 Storage），发送消息时先本地持久化→WebSocket 发送→收到 receipt 后标记已发送→失败后自动重试。与断线重连机制（F-EX-09）深度整合。
- **功能 ID**：F-EX-09（增强）
- **预期收益**：弱网环境下的消息不丢失率达到 99.9%，提升用户信任度。

#### 优化 9：会话状态 Redis 缓存层

- **问题**：会话状态查询（wait/accept/close）频繁访问数据库，高并发场景下可能成为性能瓶颈。
- **方案**：引入 Redis 缓存层，会话创建/状态变更时同步更新 Redis。设置合理的 TTL 和主动失效策略。数据库作为持久层，Redis 作为热数据层。
- **功能 ID**：F-EX-04、F-EX-07（间接优化）
- **预期收益**：会话状态查询延迟从 ~10ms（DB）降至 ~1ms（Redis），支撑 2 期实时监控面板的数据需求。

### 6.3 数据一致性策略

| 数据类型 | 缓存策略 | TTL | 降级策略 | 一致性要求 |
|---------|---------|-----|---------|-----------|
| 会员信息 | Redis 缓存 | 5 分钟 | 过期缓存 > Mock 数据 | 最终一致（5 分钟延迟可接受） |
| 商品详情 | Redis 缓存 | 10 分钟 | 过期缓存 > Mock 数据 | 最终一致（商品信息变更频率低） |
| 订单详情 | Redis 缓存 | 2 分钟 | 过期缓存 > Mock 数据 | 准实时（订单状态变更需 2 分钟内可见） |
| 优惠券详情 | **不缓存** | — | 直接 Mock 数据 | 强一致（库存和状态实时查询） |
| 优惠券领取 | **不缓存** | — | 返回错误提示 | 强一致（写操作，需实时校验） |
| 行为数据 | Redis 缓存 | 5 分钟 | 过期缓存 > Mock 数据 | 最终一致（历史行为延迟可接受） |

### 6.5 数据一致性风险点

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| Mock 数据结构与真实接口不一致 | 切换时前端渲染异常 | 中 | 定义 OpenAPI 契约文档，Mock 严格按契约生成 |
| 会员等级变更后缓存未更新 | 客服看到过期的会员等级 | 低 | TTL 5 分钟 + 手动刷新按钮 |
| 订单状态变更延迟 | 客服告知用户错误状态 | 中 | 订单卡片标注"数据更新可能有延迟"提示 |
| 优惠券领取并发冲突 | 超发或领取失败 | 低 | MVP 阶段不缓存领取操作，实时查询 |
| 外部接口超时连锁故障 | 客服系统面板加载卡顿 | 低 | 3s 超时 + 降级到缓存/Mock + 异步加载不阻塞聊天 |
