# CS 商城客服系统 — 产品需求文档（PRD）

> **文档说明**：本 PRD 基于 P01 需求调研（24 条 1 期用户故事 + 17 条 2 期用户故事）、P04 竞品分析（5 家主流客服 SaaS）、P05 功能清单（80 项功能统一编号）整合生成。功能需求第三章为本文档主体，共定义 **44 条 FR（功能需求）**，覆盖 1 期 MVP 全部 22 项功能 + 2/3 期摘要。

---

## 一、背景与目标

### 1.1 项目背景

CS 商城客服系统是商城平台的在线客服模块，为多租户商城提供"用户端—管理端—后端"三端架构的客服能力。系统基于开源项目 go-chat-service 二次开发，采用 Go / GoFrame 后端 + React / Umi Max 管理端 + Taro 4.0 用户端（小程序 + H5）技术栈。

**现状（截至 2026-06-11）**：

| 维度 | 数据 |
|------|------|
| 功能覆盖率 | **12%（9/75+ 项）** — 已具备多渠道工作台、会话转接、历史记录、快捷回复、欢迎语、排队提示、消息已读、断线重连等 9 项基础能力 |
| 能力基线 | 13 张表 / 17 组接口 / 14 个 WebSocket Action / 8 种消息类型 / 11 个管理端页面 |
| 排期硬性节点 | 开发 **6/22 启动**，V1.4 在线客服版 **8 月底上线**，不可延期 |
| 开发窗口 | 9 周（W1-W7 开发 + W8-W9 测试上线） |
| 团队配置 | 2 人（产品+前端：吕道远；后端：贺远航） |

**驱动因素**：

1. 商城 Q3-Q4 排期要求在线客服 V1.4 版 8 月底上线，112 行功能清单中当前仅完成 12%
2. 竞品（美洽、智齿、网易七鱼、容联七陌、芝麻小客服）已普遍具备 AI 客服、智能路由、知识库、全渠道接入等能力，CS 系统存在显著能力代差
3. 现有系统具备 WebSocket 实时通信、多租户、会话管理等基础能力，扩展可行

### 1.2 业务目标

| 目标层级 | 目标 | 量化指标 |
|---------|------|---------|
| **V1 上线（8 月底）** | 1 期 MVP 22 项功能交付，补齐客服核心能力闭环 | 功能覆盖率 12% → **42%**（22/75+），含 17 项 P0-Critical |
| **业务价值** | 缩短客服响应时间，提升用户满意度 | 首次响应 < 30s（目标），满意度评分基线建立 |
| **差异化** | 发挥商城原生优势，形成与第三方 SaaS 的竞争壁垒 | 订单/商品/优惠券卡片零对接，6 页面场景化入口 |
| **V2 体验（Q4）** | 2 期 19 项体验提升功能交付 | 功能覆盖率 → **67%**（41/75+），含消息预显、监控面板 |
| **长期** | 3 期 AI 智能化，对标竞品 AI 能力 | 大模型智能客服、人机协同（未纳入本期讨论） |

### 1.3 差异化定位

> **"商城原生客服系统" — 与商城业务深度耦合的一体化客服解决方案**

基于 P04 竞品分析（美洽、智齿、网易七鱼、容联七陌、芝麻小客服），CS 系统的三大差异化方向：

**方向一：业务数据零对接**

竞品（美洽/智齿/七鱼）实现订单/商品/会员数据联动需通过 CRM/API 对接，周期 2-3 个月。CS 系统内嵌于商城平台，订单卡片、商品推荐、优惠券推送、会员信息均为系统原生能力，无需任何外部集成即可实现。

- **F-034 订单卡片交互**：竞品需 CRM 对接 → CS 系统原生支持（1 期 Mock，2 期真实数据）
- **F-035 商品卡片交互**：竞品无原生支持 → CS 系统原生支持
- **F-036 优惠券卡片**：无竞品直接支持 → CS 系统创新功能（2 期）

**方向二：全渠道入口场景化**

竞品仅能传递 URL 等基础信息。CS 系统 6 个商城页面入口自动携带业务上下文：

| 入口页面 | 携带上下文 | 路由价值 |
|---------|-----------|---------|
| 商城首页 | entry=mall_home | 售前咨询分流 |
| 商品详情页 | entry=product_detail + product_id | 售前专属客服 |
| 订单详情页 | entry=order_detail + order_id | 售后专属客服 |
| 购物车 | entry=cart | 促单转化 |
| 帮助中心 | entry=help_center | 自助引导 |
| 个人中心 | entry=user_center | 会员服务 |

**方向三：零边际成本**

| 对比维度 | CS 系统 | 竞品（美洽/智齿/七鱼） |
|---------|---------|----------------------|
| 收费模式 | 无坐席许可费用 | 按坐席收费（¥1,888-4,800/坐席/年） |
| 扩展成本 | 边际成本为零 | 大规模团队成本线性增长 |
| 部署方式 | 可部署在商城自有服务器（私有化） | 私有化需额外数十万费用 |

**CS 系统核心优势矩阵**：

| 优势维度 | 说明 | 竞品对比 |
|---------|------|---------|
| 商城深度集成 | 订单/商品/优惠券/会员数据天然打通 | 竞品需 API/CRM 对接 |
| 小程序原生体验 | Taro 4.0 构建，微信小程序原生渲染 | 竞品多为 WebView/H5 嵌入 |
| 多租户架构 | `customer_id` 隔离，天然支持 SaaS 化 | 仅美洽/智齿明确支持多租户 |
| 自研可控 | Go + React 技术栈，完全自研可定制 | 竞品 SaaS 模式定制受限 |
| 私有化部署 | 可部署在商城自有服务器 | 竞品私有化需额外数十万费用 |
| 成本优势 | 无坐席许可费用，边际成本为零 | 竞品按坐席收费 |

## 二、目标用户

### 2.1 角色 R1：客服人员（管理端主要用户）

| 属性 | 描述 |
|------|------|
| **角色画像** | 商城客服团队成员，年龄 22-35 岁，日均处理 50-200 个会话 |
| **核心诉求** | 快速响应、高效处理、客户信息一目了然、话术复用 |
| **使用场景** | 登录管理端 → 查看待办面板 → 接收新会话 → 查看客户信息 → 发送回复（文字/语音/卡片） → 转接/关闭会话 → 查看评价 |
| **关键功能** | F-001 工作台、F-003 待办面板、F-005 消息撤回、F-016-019 客户信息、F-031 语音、F-034/035 卡片 |
| **痛点** | 客户信息分散需多系统切换；常见问题重复回复；无法快速定位待处理会话 |

### 2.2 角色 R2：终端用户（用户端主要用户）

| 属性 | 描述 |
|------|------|
| **角色画像** | 商城 C 端消费者，年龄 18-50 岁，技术素养跨度大，使用微信小程序为主 |
| **核心诉求** | 快速找到客服入口、便捷沟通（文字/语音）、自助解决问题、服务可评价 |
| **使用场景** | 商城浏览 → 遇到问题 → 点击页面客服入口 → 进入聊天（携带上下文）→ 浏览 FAQ → 发送消息/语音 → 提交留言（离线时）→ 会话结束评价 |
| **关键功能** | F-033 入口嵌入、F-025 FAQ、F-029 离线留言、F-030 服务评价、F-031 语音、F-032 电话、F-034/035 卡片 |
| **痛点** | 找不到客服入口；打字不方便；客服离线无反馈；无法快速自助解决常见问题 |

### 2.3 角色 R3：租户管理员（管理端配置用户）

| 属性 | 描述 |
|------|------|
| **角色画像** | 商城客服主管或运营负责人，管理 5-50 人客服团队 |
| **核心诉求** | 高效分配会话、维护话术库、监控服务质量、配置自动化规则 |
| **使用场景** | 配置路由规则 → 维护知识库 → 配置敏感词 → 设置超时策略 → 查看评价统计 → 管理留言 |
| **关键功能** | F-004 智能路由、F-006 敏感词、F-007 超时关闭、F-022 知识库、F-024 评价管理、F-008 留言管理 |
| **痛点** | 会话分配依赖人工；话术无标准参考；无法统一管控服务质量 |

### 2.4 角色 R4：系统集成对接方（外部系统）

| 属性 | 描述 |
|------|------|
| **角色画像** | 商城后端开发团队，负责提供会员/商品/订单/营销数据接口 |
| **核心诉求** | 接口契约清晰、Mock/真实可切换、数据安全可控 |
| **使用场景** | 定义接口契约 → 提供 Mock 数据 → 联调测试 → 真实接口上线 |
| **关键功能** | F-056 API 对接、F-057 缓存策略、F-058 Mock 切换 |
| **痛点** | 接口未就绪阻塞开发；数据一致性难以保证 |

## 三、功能需求

> **说明**：本章为 PRD 主体，共定义 **44 条 FR（功能需求）**。其中 1 期 MVP 22 条（FR-01 ~ FR-22，含 P0-C 17 项 + P0-N 5 项），2 期 14 条（FR-23 ~ FR-36），3 期 8 条（FR-37 ~ FR-44，分类摘要）。
>
> 每条 FR 含：编号、名称、描述、验收标准、优先级、关联功能 ID（对应 P05 功能清单 F-001~F-080）、关联用户故事 ID。

### 3.1 1期 MVP — P0-Critical（17 项，上线必须）

#### FR-01 智能路由与分流规则引擎

| 字段 | 内容 |
|------|------|
| **功能ID** | F-004 |
| **用户故事** | US-MVP-02 |
| **优先级** | P0-Critical |
| **复杂度** | L（5d） |
| **描述** | 客服管理员可配置路由规则，按入口标签/用户属性/关键词匹配，将用户会话自动分配给合适的客服，替换现有简单的 `is_auto_accept` 自动接入逻辑。 |
| **验收标准** | AC1: 支持创建路由规则（匹配方式：入口标签 / 用户属性 / 关键词 / 兜底）<br>AC2: 支持分配策略（轮询 / 空闲优先 / 指定客服 / 技能组）<br>AC3: 规则按优先级从高到低匹配，第一条命中即执行<br>AC4: 兜底规则有且仅有 1 条<br>AC5: 列表支持拖拽排序调整优先级<br>AC6: 支持启用/关闭切换<br>AC7: 排队超时（可配）自动溢出转接 |

| **依赖** | 依赖 F-033（入口嵌入传递 entry_tag 参数） |

#### FR-02 消息撤回

| 字段 | 内容 |
|------|------|
| **功能ID** | F-005 |
| **用户故事** | US-MVP-03 |
| **优先级** | P0-Critical |
| **复杂度** | M（2d） |
| **描述** | 客服人员或终端用户可在发送消息后 2 分钟内撤回已发送消息，撤回后双方均不可见内容（数据库保留用于审计）。 |
