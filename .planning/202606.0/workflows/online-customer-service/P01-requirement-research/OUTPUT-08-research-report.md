## 执行摘要

本报告基于 CS 客服系统代码库扫描、排期表功能清单（112 行）、B 泳道 PRD 文档、开源选型报告等多源数据，完成在线客服系统的全面需求调研。

**核心发现**：

- 当前系统已具备 9 项功能（约 12% 覆盖率），具备 WebSocket 实时通信、多租户、会话管理等基础能力
- 1期-MVP 需新增 **24 项功能**，开发窗口 **9 周**（6/22 - 8月底），时间紧、任务重
- 其中 **6 项功能依赖外部系统**（商城会员库、商品库、OMS、营销中心），MVP 阶段采用 Mock 数据策略
- 排期硬性节点：V1.4 在线客服版 **8 月底上线**，不可延期
- 2期规划 17 项体验提升功能，3期 25+ 项 AI 智能化功能暂不纳入

**关键决策建议**：

1. 优先交付 14 项 P0-Critical 功能，确保核心业务闭环
2. 外部系统对接全部 Mock 先行，接口契约提前定义
3. 6 页面入口嵌入与路由引擎为最高优先级，决定用户触达和会话分配质量
4. 知识库是 FAQ 快捷问题和 AI 客服的数据基础，W3 必须完成

## 1. 调研背景与范围

### 1.1 项目背景

CS 客服系统是商城平台的在线客服模块，采用三端架构：

- **后端** (Go/GoFrame)：提供 HTTP API + WebSocket 实时通信
- **管理端** (React/Umi Max)：客服人员使用的管理后台
- **用户端** (Taro/React)：终端用户使用的聊天界面（小程序 + H5）

系统基于开源项目 go-chat-service 二次开发，已具备基础聊天能力。

## 4. 技术可行性分析

### 4.1 可行性评估

| 技术点 | 可行性 | 风险 | 说明 |
|--------|--------|------|------|
| 路由引擎 | 高 | 中 | 基于现有 auto_rules 扩展，DFA 匹配 |
| 敏感词过滤 | 高 | 低 | 成熟算法（DFA），词库 < 1万性能无忧 |
| 消息撤回 | 高 | 低 | 增加字段 + WebSocket action |
| 会话超时 | 高 | 低 | cron.go 框架已搭建 |
| 知识库 | 高 | 低 | 标准 CRUD，表设计参考 B 泳道 PRD |
| 语音消息 | 高 | 中 | 需小程序录音权限审核 |
| 卡片消息 | 高 | 低 | 扩展消息类型 + JSON Schema |
| 离线留言 | 高 | 低 | 新建表 + 表单组件 |
| 服务评价 | 高 | 低 | 多维度评价替换现有 rate 字段 |
| 客户信息 | 高 | 低 | Mock 先行，接口契约已定义 |
| 外部系统对接 | 中 | 高 | Mock 降低 1期风险，2期对接真实系统 |

### 4.2 技术债务评估

| 债务项 | 严重程度 | 处理建议 |
|--------|---------|---------|
| 数据库缺少 deleted_at 软删除 | 低 | messages 表缺少 deleted_at，1期增加 revoked_at 即可 |
| 无数据库迁移工具 | 中 | 建议引入 golang-migrate 管理迁移脚本 |
| 前端无状态管理（管理端） | 低 | valtio proxy 已满足，无需升级 |
| 无 API 文档 | 中 | 建议引入 Swagger/OpenAPI 自动生成 |
| 无自动化测试 | 高 | 1期测试阶段需补充核心链路测试 |

## 9. 结论与建议

### 9.1 核心结论

1. **1期-MVP 范围合理**：24 项功能覆盖客服系统核心能力，P0-C 14 项构成最小可用产品
2. **技术方案可行**：基于现有代码扩展，无需引入新技术栈，降低技术风险

4. **外部依赖可控**：6 项外部依赖功能全部 Mock 先行，不影响 1期交付
